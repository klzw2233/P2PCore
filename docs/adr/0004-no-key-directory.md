# Key Directory 移出核心库

核心库只认 Peer ID,**不提供**"人类可读标识 → 公钥"的目录服务。服务端设施因此只剩 Discovery Server 与 Relay,两者都不掌握任何密钥。

## 为什么记录这个决定

项目最初规划服务端提供 Key Directory,本决定推翻了它。读者会立刻问:"那用户怎么加好友?"

## 推导

Peer ID 就是 Identity Key 的公钥,因此**只要持有对方的 Peer ID 就已经持有其公钥**,拨号在密码学上是自认证的,中间人攻击在结构上无法发生。Key Directory 唯一的作用是把可记忆的标识映射到不可记忆的公钥——而这个映射不可信,它是"防御恶意服务端"这条威胁在整个系统中的**唯一来源**。

移除它,该威胁便从"依赖用户老实比对 SAS 来缓解"变成"不存在这个攻击面"。这不是缓解,是消除。

此外,"用户名 → 公钥"是应用语义而非传输语义,它违反了核心库不含应用语义的范围约定,本就不该在这里。

## 后果

- **交换 Peer ID 是应用层的事**:面对面扫二维码、复制粘贴、或任何带外渠道。核心库不关心。
- **SAS 仍然保留**,因为 Peer ID 同样可能经由不可信渠道到达(网页、他人转发)。渠道决定初始 Trust State:面对面扫码属可信渠道,直接进入 Verified;粘贴或转发而来的属不可信渠道,进入 TOFU,需 SAS 补验证。
- 需要用户名的应用可在上层自建目录,并自行承担其信任风险——它比核心库更清楚自己的用户模型。
- 移除了一个子系统、一套协议、一批对抗性测试和一个运维组件。本决定的成本是负的。
