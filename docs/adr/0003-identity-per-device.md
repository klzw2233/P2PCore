# 一个 Identity Key 对应一台设备,核心库不建模"用户"

一个 Identity Key 唯一对应**一台设备**,而非一个人。同一个人的手机与电脑是两个独立的 Peer,各自持有互不相关的 Identity Key,需要**分别**完成 SAS 验证。核心库中不存在"用户"这一概念。

## 为什么记录这个决定

多设备是即时通讯类系统最常见的需求,读者看到"张三的手机"和"张三的电脑"在系统中毫无关联,会认为这是尚未实现的缺陷。它是刻意的。

## 考虑过的替代方案

- **一个用户一个 Identity Key,多设备共享私钥**:已排除,且不只是次优而是错误。私钥同步意味着私钥必须离开设备,同步渠道构成全新攻击面,一台设备失窃即导致全部设备沦陷,且无法单独撤销任何一台。
- **主身份 + 设备子密钥交叉签名**(Signal、Matrix 采用的模型):这是正确的终局形态,但它本身就是一套完整的设备管理与背书协议,复杂度与整个 Trust Layer 相当,不适合作为第一版的负担。

选择"一设备一身份"还因为它与已有决定自洽:Session 要求双方同时在线,因此连接的对象本来就是**一个在线的端点**,而不是一个抽象的"人"。设备天然就是连接单位。

## 后果

- **人工验证成本是 N²。** 双方各有 N 台设备时,需要两两验证。这是本决定最真实的代价,可接受但必须向上层应用说明。
- **必须保留向主身份模型演进的可能。** 这是一条硬约束,不是愿望:**Trust State 必须以设备公钥为主键**,不得以任何用户级标识为主键;其记录形态应能容纳日后追加的背书字段。违反这一条,加入主身份背书层将需要推翻数据模型重写。
- "用户"这一概念归属上层应用。把若干 Peer 呈现为"同一个人的多台设备",是应用层的展示逻辑,核心库不提供也不承认这种聚合。
